# 选题说明

## 一、项目题目

**CampusClaw：支持知识库、提示词模板、Skill 与 MCP 的个人 AI 应用平台**

所属课程：互联网软件技术开发与实践
当前阶段：个人项目（后续合作尚未开始）

本项目以课程学习场景为基础，已实现多个 AI 应用、可管理提示词模板、知识库检索、内置及上传 Skill、外部 HTTP/MCP 工具接入，形成可部署、可演示、可验证的个人 AI 应用平台。

本说明区分个人阶段已完成能力与后续可选建设。后续合作应直接复用已完成模块，不重复开发；尚未实现的教学业务须另行明确需求、负责人和验收场景，再通过 OpenSpec 实施。

## 二、项目背景与建设目标

课程资料通常分散在多个文件中，学生查找知识点需要反复翻阅，教师也难以从资料访问和答疑过程判断学生掌握情况。直接使用通用聊天工具，又可能得到脱离课程材料、缺少依据的回答。

现有系统已解决班级资料共享和基于资料的检索问答问题。后续建设重点是把这些能力用于实际学习过程：学生能够查资料、核对答案出处、完成练习并回顾错题；教师能够根据本班资料组织测验，并查看题目正确率和学生完成情况。

项目的目标是形成“教师上传资料 → 学生检索与答疑 → 教师发布练习 → 学生作答 → 教师查看反馈”的完整流程，同时通过对照实验展示检索与引用机制的效果。

### 3.2 后续增量建设功能（尚未实现，不属于本次交付）

#### 1. 课程章节与资料组织

在现有班级范围内增加章节目录和资料归属。教师可以创建章节、调整资料分类；学生可以按章节浏览资料，检索和问答可以选择章节范围。

首版沿用“一个账号属于一个班级”的现有模型，将章节作为班级内部的教学单元，不引入跨班选课、多角色切换或复杂教务管理。

#### 2. 答疑记录与问题反馈

复用现有新应用的私有执行记录和来源快照能力；新增的是旧资料问答的持久会话、学生反馈及教师未解决问题处理，不重复建设模型调用记录页面。

学生可以保存和查看自己的问答记录，回看回答引用的原文，并提交“有帮助”“未解决”等反馈。教师查看本班未解决问题列表，用于补充教学材料或调整讲解内容。

学生只能访问自己的记录；教师查看用于教学改进的本班问题和反馈，不提供任意浏览学生全部私人会话的入口。历史记录保留当时的回答与来源快照；原材料被删除或重建后，页面提示来源状态，避免旧引用指向新的切片。

#### 3. 基于资料的辅助出题与教师审核

复用已完成的“练习生成”应用、提示词、Skill 和有限证据检索；新增的是结构化题库、教师审核、发布状态与来源快照，不重复实现基础练习文本生成。

教师选择本班章节或材料后，系统从有限资料片段生成候选练习题，包含题干、选项、参考答案、解析和来源。首版限定为单选题、判断题，同时允许教师手工录入和修改。

生成结果先保存为草稿，教师核对内容和来源后才能发布。格式错误、引用无效或证据不足的候选题不能直接发布；模型服务不可用时，教师仍可手工建题。AI 负责辅助准备题目，教师负责确认教学正确性。

#### 4. 在线练习与错题回顾

教师从审核后的题目中组建并发布章节测验，设置提交截止时间。学生完成作答后获得客观题评分；截止后统一开放正确答案、解析与来源，减少提前泄露答案对测验的影响。

首版每名学生每次测验保留一次正式提交，提交前可以保存草稿。系统记录错题，学生在答案开放后可按章节回顾并跳转到相关资料。主观题自动评分、自适应组卷和考试监考不纳入首版。

#### 5. 教师学习情况看板

按章节和测验展示参与人数、提交率、平均分、各题正确率及未解决问题数量。学生查看个人成绩和错题，教师查看本班汇总以及本班测验的学生提交情况。

统计给出明确口径：提交率按正式提交人数除以测验发布时的应参与人数计算，平均分只统计正式提交，各题正确率以正式提交中答对该题的人数为分子。统计结果用于辅助教学，不把少量答题记录直接解释为完整的学生能力画像。

### 3.3 可选提高项

在核心流程完成并验收后，可优先选择一项继续提高，不将全部扩展同时列为必做项：

- **文本型 PDF 导入**：提取可选择文本的 PDF 内容并记录页码，复用切片与检索流程；扫描件 OCR、复杂公式和图表理解暂不承诺。
- **索引后台任务**：将耗时的资料处理交给后台任务，显示等待、处理中、成功、失败及重试状态。
- **检索效果实验页面**：针对同一问题比较关键词、向量与混合检索的结果和耗时，辅助课程答辩展示。

## 四、技术方案

### 4.1 总体架构与技术选型

延续当前单体 Web 应用结构，通过业务模块划分职责，降低重构成本。浏览器通过受保护的 HTTP API 访问 Flask；Flask 负责权限校验、业务处理和模型调用，MySQL 存储业务数据与正文，Qdrant 存储向量及来源标识，上传原文件保存在服务端持久目录。

| 层次 | 技术方案 | 用途与调整 |
| --- | --- | --- |
| 页面层 | 现有 HTML 模板、CSS、原生 JavaScript | 扩展章节、问答记录、教师题库、测验、错题和统计页面，复用认证请求封装。 |
| 业务层 | Python、Flask | 按章节、问答记录、题库、测验和统计拆分业务模块，统一校验输入及权限。 |
| 关系数据层 | MySQL 8、SQLAlchemy | 保存账号、班级、资料正文，以及新增章节、题目、提交和反馈数据；SQLite 继续用于适合的本地测试。 |
| 检索层 | MySQL 正文索引、Qdrant | 复用现有关键词与向量检索，通过 RRF（倒数排名融合）合并候选结果。 |
| 模型接入层 | 现有课程网关的嵌入与对话接口 | 复用服务端适配器；模型名、地址和密钥由私有配置提供。 |
| 部署与测试 | Docker Compose、pytest | 延续现有部署方式和测试体系，补充新业务的权限、状态流转及异常场景验证。 |

首版不强制引入新的前端框架、微服务或额外消息中间件。若选择后台索引提高项，再通过独立 OpenSpec change 确定任务队列与工作进程方案。

### 4.2 核心数据设计

保留现有 `classes`、`users`、`materials`、`knowledge_entries`、`knowledge_chunks`，以及个人阶段新增的 `prompt_templates`、`uploaded_skills`、`connector_bindings`、`application_runs`；后续仅按需求增加以下业务实体：

| 实体 | 主要数据与关系 |
| --- | --- |
| 章节 | 班级、名称、顺序；资料关联章节，已有资料可先归入“未分类”。 |
| 问答记录与反馈 | 所属用户、班级、问题、回答、引用快照、时间、反馈状态。 |
| 题目与来源 | 班级、章节、题型、题干、选项、正确答案、解析、审核状态、来源快照。 |
| 测验与测验题目 | 班级、标题、截止时间、发布状态、题目快照、分值和应参与学生名单。 |
| 提交与作答明细 | 测验、学生、草稿或正式提交状态、作答、得分及提交时间。 |

错题首版从正式提交的错误作答中查询生成，统计也从业务数据计算，避免维护多份容易不一致的数据。测验发布后固定题目和评分依据，后续修改题库不改变已发布测验及历史成绩。

数据表通过外键、唯一约束和事务保持一致性，特别是限制同一学生对同一测验重复正式提交。数据库结构升级须提供迁移与回退说明，不以清空现有数据作为升级手段。

### 4.3 检索增强问答与出题流程

问答继续采用 RAG（检索增强生成）：先确定用户有权访问的班级和章节，再执行混合检索、筛选有限证据，最后生成并校验带来源的回答。问答历史用于回顾；首版继续按当前问题检索，不默认加入跨轮指代改写。

辅助出题复用资料访问和证据获取能力，流程为：

1. 教师选择本班材料或章节，并指定有限的出题数量与题型。
2. 服务端选取有界的来源切片，将其作为资料数据交给模型，资料中的指令不得覆盖服务端规则。
3. 模型返回结构化候选题，服务端校验必填字段、选项数量、答案范围和引用有效性。
4. 候选题进入草稿，教师核对知识内容、答案与出处后审核。
5. 仅审核通过的题目可加入待发布测验，发布时生成不可变的题目快照。

引用存在并不意味着内容一定正确，结构校验也不能代替教师审题。系统需明确标记 AI 生成草稿，并保留教师修改和审核结果。

### 4.4 权限与可靠性设计

- 延续 JWT Bearer 认证：浏览器使用 `sessionStorage` 保存 token，受保护请求通过 `Authorization` 请求头携带，不恢复 Cookie 登录路径。
- 服务端依据当前数据库身份确定角色与班级，所有新增记录、题目、测验、成绩和统计都进行班级及资源归属校验。
- 学生提交接口只接收作答内容，成绩由服务端计算；答案开放前，学生接口不返回正确选项、解析或可泄露答案的来源快照。
- 正式提交在事务中检查截止时间、发布状态和重复提交条件，避免并发请求产生重复成绩。
- 对模型调用设置超时、输入上限和调用频率限制；运行日志记录耗时与错误类型，不记录密钥或完整敏感请求内容；本人授权可见的应用执行记录按已实现的独立权限边界保留请求与响应，不公开为系统日志。
- 模型或向量服务异常时给出明确提示；资料浏览、人工建题、已发布测验的作答与评分应可继续使用。
- 展示资料、模型回答和反馈时进行安全转义；私有 `.env`、数据库文件、容器数据及备份不得提交到版本库。

## 六、验收与效果评价

### 6.1 后续增量功能验收（待实施）

准备两个班级及各自师生账号，用同一组演示数据覆盖以下流程：

1. 教师创建章节、上传资料；本班学生可浏览，其他班级用户不可访问。
2. 学生提问并核对来源；无相关证据时明确返回未找到内容，并可提交问题反馈。
3. 教师生成或手工建立候选题，修改并审核后发布测验；未审核题目不能发布。
4. 学生保存作答草稿并正式提交，系统正确评分；重复提交和截止后提交被拒绝。
5. 答案开放前，学生无法通过页面或 API 获取参考答案；开放后可以查看解析、来源和错题。
6. 教师看板与预先人工计算的提交率、平均分、题目正确率一致。
7. 模型接口超时或不可用时，人工建题与已发布测验流程仍可完成。

### 6.2 后续检索与回答效果评价（待开展）

建立不少于 30 个带人工标注的课程问题，覆盖直接事实、同义表达、跨片段比较及无答案问题。分别测试关键词、向量和混合检索，记录以下指标：

- **检索命中率 Hit@5**：对于有答案的问题，前五条结果至少命中一个人工标注相关片段的问题比例。
- **回答依据充分率**：人工检查有答案问题的回答，其主要结论是否均有对应来源支持。
- **无答案处理正确率**：无答案问题中，系统正确返回资料不足提示的比例。
- **响应耗时**：分别记录检索与问答的中位数、P95 耗时，并注明运行环境、样本量和模型配置。

拟定课程验收目标为 Hit@5 不低于 80%、回答依据充分率不低于 90%、无答案处理正确率不低于 90%；这些是待验证目标，不是现有测试结论。开发调参样例与最终评测问题应分开，固定评测集后报告实际结果、失败案例和原因，不预设混合检索一定优于其他方法。

## 七、个人阶段成果与后续目标

个人阶段的特色是可组合的 AI 应用、受控知识上下文、可上传技能与可追溯工具调用。后续目标是将班级权限、可追溯知识库与教学练习串联起来：回答和候选题都有可核对的资料来源，AI 生成题目经过教师审核，练习结果能够反映到教学反馈中。检索对照实验和失败案例分析则为技术效果提供可检验的依据。

预期成果是一套适合小规模班级使用的智能助学原型，能够完整展示 Web 开发中的认证授权、数据建模、业务状态流转、检索与模型服务集成、测试和容器化部署，满足课程大作业对功能完整性、技术深度和工程实践的综合要求。
